# Mini NPU Simulator · Codyssey E1-3

## 실행 환경과 방법

- 요구 환경: Python 3.8 이상, 외부 패키지 설치 없음
- 검증 환경: WSL 2 Ubuntu-26.04, Python 3.14.4, Linux 6.18.54.1-microsoft-standard-WSL2
- 검증일: 2026-11-09

```bash
git clone https://github.com/Eungho-LEE/codyssey_test3.git
cd codyssey_test3
python3 main.py
```

Windows Python에서는 `py -3 main.py`로 실행할 수 있습니다. `data.json`은 `main.py`와 같은 폴더에 둡니다. 파일 경로는 `__file__` 기준이므로 다른 작업 폴더에서 실행해도 같습니다. 실행 중 코드를 고쳤다면 저장한 뒤 메뉴의 `0`으로 종료하고 다시 실행해야 반영됩니다.

| 메뉴 | 입력과 결과 |
| --- | --- |
| `1` | 필터 A 3행 → 필터 B 3행 → 저장 확인 → 패턴 3행 → 점수·판정·3×3 평균 시간 |
| `2` | data.json 로드 → 케이스별 검증·판정 → 3·5·13·25 크기 성능 표 → 총합·실패 원인 |
| `3` | N 입력 → Cross/X 생성 → 패턴 선택 → 기존 모드 1 판정 재사용 → 2D/1D 성능 비교 |
| `4` | 동일 생성 입력으로 3·5·13·25 크기의 2D/1D MAC 비교 |
| `0` | 종료 |

## 구현 요약

| 함수 | 역할 |
| --- | --- |
| `mac` | 이중 반복문으로 위치별 곱의 합 계산 |
| `read_grid` | 한 줄 숫자 3개, 숫자 변환, 유한값 검사와 현재 행 재입력 |
| `load_data` | UTF-8/BOM JSON 로드, 최상위 filters·patterns 객체 검사 |
| `normalize_label` | 공백·대소문자 정리 후 `+`·`cross` → Cross, `x` → X |
| `prepare_case` | size_N_idx에서 크기 추출, 필터 선택, 필드·라벨·격자 검증 |
| `decide` | 절대 점수 차이가 `1e-9` 미만이면 UNDECIDED, 그 외 큰 점수 라벨 |
| `average_mac_ms` | 한 필터의 MAC 호출 구간을 10회 측정하고 평균 ms 반환 |
| `benchmark_data` | 3×3 데모와 JSON의 5·13·25 크기별 측정 |
| `print_report` | 전체·통과·실패 수와 실패 케이스별 사유 출력 |

`data.json`은 filters의 size_5·size_13·size_25 필터 묶음과 patterns의 size_N_idx 케이스를 중첩 객체로 보관합니다. 각 케이스는 input 격자와 expected를 가집니다. 두 필터와 패턴이 같은 N×N인지 검사하고, 잘못된 케이스는 FAIL로 기록한 뒤 다음 케이스를 처리합니다. 벡터화·NumPy·pandas를 사용하지 않습니다.

MAC의 작은 계산 예시는 `pattern=[[2,3]]`, `filter=[[4,5]]`일 때 `total=0 → 0+2×4=8 → 8+3×5=23`입니다. 이는 계산 함수의 원리를 보이는 1×2 예시이며, 실제 수동 모드 입력은 3×3입니다.

### 모드 1과 모드 2의 판정·출력·집계 비교

두 모드는 **같은 `decide()`와 같은 EPSILON**을 사용합니다. 차이는 과제 요구에 따른 라벨의 의미, 사용자 표시, 정답 비교와 집계 여부입니다.

| 구분 | 모드 1: 사용자 입력 | 모드 2: data.json 분석 |
| --- | --- | --- |
| 필터 라벨 | 사용자가 입력한 A·B | 정규화한 Cross·X |
| 승리 판정 | 점수가 큰 쪽의 A 또는 B | 점수가 큰 쪽의 Cross 또는 X |
| 동점 경계 | `abs(a-b) < 1e-9` | 동일한 조건 |
| 동점 내부 반환값 | `UNDECIDED` | `UNDECIDED` |
| 동점 화면 표시 | `판정: 판정 불가` | `판정=UNDECIDED` |
| 정답 expected | 입력받지 않음 | 필수이며 Cross 또는 X로 정규화 |
| PASS·FAIL | 정답 비교와 집계 없음 | predicted와 expected가 같으면 PASS, 다르면 FAIL |
| 동점의 집계 | 판정 불가만 표시 | 유효 expected는 Cross/X이므로 UNDECIDED는 FAIL로 집계 |
| 구조·라벨 오류 | 현재 행을 재입력받음 | 해당 케이스를 FAIL로 기록하고 다음 케이스 계속 처리 |
| 최종 출력 | 점수·판정·3×3 평균 시간 | 케이스별 결과·크기별 시간·전체/통과/실패·실패 사유 |

차이가 정확히 EPSILON이면 동점이 아니며, 수동 모드에서만 내부 문자열 `UNDECIDED`를 사용자 문구 `판정 불가`로 매핑합니다. `1e-9`는 과제의 권장 예시를 채택한 절대오차 기준이지 모든 수치 범위에 대한 오차 보장은 아닙니다. 데이터의 크기·값 범위·누적 오차가 달라지면 도메인에 맞는 절대오차나 상대오차의 조합을 검토하고, 경계 검사와 기존 결과 비교를 함께 수행해야 합니다.

### 라벨 별칭과 단위 검사

| 입력 예시 | 표준 라벨 | 적용 위치 |
| --- | --- | --- |
| `+`, `cross`, `Cross`, `CROSS`, ` Cross ` | Cross | expected와 필터 키 |
| `x`, `X`, ` x ` | X | expected와 필터 키 |
| `unknown` 또는 문자열 아닌 값 | 허용하지 않음 | 케이스별 오류 및 FAIL |

`normalize_label()`을 별도로 두어 expected와 필터 키가 같은 규칙을 공유하며, 정규화만 독립적으로 검사하거나 별칭을 추가할 수 있게 했습니다. 다음은 저장소 폴더에서 실행할 수 있는 최소 단위 검사입니다.

```bash
python3 -c "from main import normalize_label; assert normalize_label('+') == 'Cross'; assert normalize_label(' Cross ') == 'Cross'; assert normalize_label('x') == 'X'; print('라벨 검사 통과')"
```

지원하지 않는 라벨의 예시 출력은 `size_5_1: FAIL - 지원하지 않는 라벨: unknown`이며, 실제 기록은 [label.txt](docs/records/label.txt)에 있습니다.

### 신규 라벨 추가 절차

현재 과제의 표준 라벨은 Cross/X 두 개이며, 아래는 향후 확장 시 수행할 체크리스트입니다. **같은 의미의 별칭 추가**와 **새 패턴 종류 추가**를 구분해야 합니다.

1. **정규화:** 같은 의미의 별칭이면 `normalize_label()`의 aliases에 기존 Cross/X로 연결합니다. 새 종류(예: Circle)라면 표준 이름과 허용 별칭을 먼저 정의합니다. 단, 현재 과제의 Cross/X 필수 조건은 유지합니다.
2. **데이터·검증:** 해당 크기의 필터와 expected 예시를 준비하고 `select_filters()`의 필수 라벨 검사·중복 검사·`prepare_case()`의 크기 검증을 함께 점검합니다.
3. **판정:** 별칭 추가만으로 두 필터 판정은 바뀌지 않습니다. 세 번째 종류를 지원하려면 `analyze_cases()`의 Cross/X 고정 호출과 결과 필드를 확장하고, `decide()`를 여러 점수 중 최댓값 및 epsilon 이내 공동 최댓값을 처리하는 방식으로 재설계해야 합니다. aliases에 Circle만 넣어서는 세 종류 판정이 구현되지 않습니다.
4. **출력·집계:** 수동 A/B 모드를 유지할지 라벨 선택을 확장할지 정하고, 케이스별 점수·판정·expected·실패 사유와 `print_report()`를 일치시킵니다. 최상위 점수가 동점이면 UNDECIDED로 표시하고 expected와 다르면 FAIL로 세는 정책도 명시합니다.
5. **테스트:** 별칭·공백·대소문자, 알 수 없는 라벨, 중복 필터, 새 라벨 정상 판정·동점·잘못된 expected를 검사합니다. 기존 공식 6개 결과가 유지되는지 회귀 검증하고 README의 라벨 표와 예시를 갱신합니다.

## 결과 리포트

공식 파일을 변경하지 않고 실행한 실제 기록은 [official_data.txt](docs/records/official_data.txt)에 있습니다.

| 케이스 | Cross 점수 | X 점수 | 판정 | expected 정규화 | 결과 |
| --- | --- | --- | --- | --- | --- |
| size_5_1 | 0.9 | 0.9 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.7 | X | X | PASS |
| size_13_2 | 7.5 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.9 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

1. 실제 제공 파일에는 총 6개 케이스가 있으며 통과 3개, 실패 3개입니다.
2. size_5_1은 두 점수가 약 0.9로 같아 UNDECIDED이지만 expected는 X여서 실패합니다.
3. size_13_2는 두 점수가 약 7.5로 같아 UNDECIDED이지만 expected는 Cross여서 실패합니다.
4. size_25_1은 두 점수가 약 4.9로 같아 UNDECIDED이지만 expected는 X여서 실패합니다.
5. 나머지 세 케이스는 큰 점수의 표준 라벨이 expected와 일치해 통과합니다.
6. 이 세 동점 FAIL은 데이터와 비교 정책에 따른 분석 결과이며 프로그램 예외 종료를 뜻하지 않습니다.
7. expected의 `+`와 `x`, 필터 키의 `cross`와 `x`를 정규화해 표기 차이로 인한 오판정을 방지했습니다.
8. 부동소수점의 미세한 차이로 승패가 달라지지 않도록 반올림 전 점수 차이에 절대 허용오차를 적용합니다.
9. `abs(a-b) < 1e-9`가 동점 조건이므로 차이가 정확히 1e-9인 경우는 동점에 포함하지 않습니다.
10. 동점을 임의로 X나 Cross로 바꾸거나 expected를 수정해 통과 수를 늘리지 않았습니다.
11. 한 필터의 N×N MAC은 N²개 위치를 방문하고, 각 위치에서 곱셈과 누적 덧셈을 수행합니다.
12. 따라서 한 필터의 시간 복잡도는 O(N²)이고, 두 필터를 계산해도 상수배 차이여서 O(N²)입니다.
13. 표의 N²는 곱셈·덧셈을 묶은 MAC 위치쌍 수이며, 산술 연산을 각각 세면 대략 2N²입니다.
14. 측정에는 파일 읽기·입력·출력·검증을 포함하지 않고 MAC 함수 호출 구간만 포함합니다.
15. 크기마다 10회 측정한 합계를 10으로 나누고 초를 ms로 변환했습니다.
16. 작은 입력은 함수 호출·시계 측정·OS 스케줄링 영향 때문에 시간 비율이 N² 비율과 정확히 같지는 않습니다.
17. 아래 결과에서는 크기가 커질수록 시간이 증가하지만, 한 번의 측정으로 정확한 성능 배율을 일반화하지 않습니다.
18. 이 프로그램은 CPU에서 실행하는 계산 시뮬레이터이며 실제 NPU의 병렬 처리 성능을 측정하지 않습니다.

### 실패 원인과 처리 비용 분석

**동점 세 케이스:** size_5_1·size_13_2·size_25_1은 두 필터와의 가중 합이 epsilon 이내로 같지만 expected는 각각 X·Cross·X입니다. 두 점수를 구하는 비용은 케이스당 `2N²` MAC 위치쌍이며, 비교 자체는 O(1)입니다. 각각 50·338·1,250 위치쌍을 계산한 뒤 동점 때문에 FAIL이 됩니다. 이는 크기 오류나 라벨 누락으로 계산을 건너뛴 FAIL과 원인이 다릅니다. 실패 요약의 `동점(UNDECIDED)`는 위 결과 표의 두 점수와 expected를 함께 보아야 합니다.

**라벨·스키마 오류:** 알 수 없는 라벨은 정규화 단계에서, 누락 input 등은 필드 접근 단계에서 검출합니다. 라벨 문자열 길이를 L이라 하면 strip·lower 등의 정규화는 O(L)입니다. 검사 순서에 따라 이 오류들은 MAC 전에 끝납니다. 형식을 맞추지 않은 값을 임의로 보정하지 않고 실패 이유를 기록해, 정상 케이스의 계산을 계속 진행합니다.

**격자 크기·숫자 오류:** 바깥 행 수 불일치는 길이 검사에서 바로 검출할 수 있고, 열 수·숫자 유한성 검사는 오류 위치까지 순회합니다. 유효 격자 하나를 끝까지 검사하는 최악의 비용은 O(N²)이며 두 필터와 패턴 세 개 검사도 O(N²)입니다. 실패한 케이스는 MAC을 수행하지 않으므로, 오류 처리 시간과 유효 케이스의 MAC 성능 표를 같은 의미로 비교하지 않습니다.

### MAC 점수와 패턴의 관계

| 패턴 | Cross 필터 점수 | X 필터 점수 | 해석 |
| --- | --- | --- | --- |
| 십자 `010 / 111 / 010` | 5 | 1 | 같은 위치의 1이 Cross와 다섯 곳, X와 중심 한 곳에서 겹침 |
| X `101 / 010 / 101` | 1 | 5 | X 필터와 겹치는 다섯 위치에서 점수 누적 |
| 모두 0 `000 / 000 / 000` | 0 | 0 | 어느 필터에도 양의 기여가 없어 동점 |

위 예시는 같은 크기의 0/1 격자에서 겹치는 위치가 늘면 점수가 증가함을 보여 줍니다. 일반적인 가중치·음수·크기가 다른 입력에서는 값의 크기와 부호도 점수에 영향을 주므로, 원시 MAC 점수를 정규화된 유사도나 확률로 해석하지 않습니다.

### 실제 성능 측정

아래는 검증 실행 한 번에서 나온 값입니다. 한 필터·한 패턴 기준이고, 3×3은 데모 격자, 나머지는 각 크기의 첫 유효 케이스와 Cross 필터를 사용했습니다.

| 크기 | 평균 시간(ms) | MAC 위치쌍 수 N² | 반복 |
| --- | --- | --- | --- |
| 3×3 | 0.000616 | 9 | 10 |
| 5×5 | 0.000875 | 25 | 10 |
| 13×13 | 0.003791 | 169 | 10 |
| 25×25 | 0.012656 | 625 | 10 |

두 필터를 한 번씩 계산하면 `2×N²` MAC 위치쌍(곱셈·덧셈을 따로 세면 대략 `4×N²` 산술 연산)입니다. 표는 한 필터 기준이므로 두 필터 전체 시간과 혼동하지 않습니다. 현재는 최소 요구인 평균값만 측정합니다. 측정 분산을 더 분석하려면 동일 조건의 10개 개별 경과 시간을 보관해 최소·최대·표준편차를 함께 보고할 수 있지만, 이번 표에는 측정하지 않은 보조 통계를 만들어 넣지 않았습니다.

### 대규모 처리: 1000×1000에서의 예상 병목과 최적화 순서

현재 JSON 모드는 5·13·25만 지원합니다. 아래는 크기 지원을 확장했을 때의 설계 분석으로, 1000×1000을 실제 실행·측정한 결과가 아닙니다. 수동 모드도 현재 3×3입니다.

| 항목 | 1000×1000에서의 작업량 또는 한계 |
| --- | --- |
| 한 필터 | 1,000,000 MAC 위치쌍, 시간 O(N²) |
| 두 필터 | 2,000,000 위치쌍, 약 4,000,000 곱셈·덧셈 |
| 한 필터 10회 측정 | 10,000,000 위치쌍을 방문하며 반복 횟수만큼 비용 증가 |
| 메모리 | 패턴 하나와 필터 두 개를 보관하면 총 3,000,000개 값의 참조 및 숫자 객체 필요 |
| JSON 로드 | 문서 전체를 읽어 중첩 list로 만들므로 텍스트와 Python 객체의 메모리·파싱 비용 발생 |
| 실행 | Python 중첩 반복·인덱싱·숫자 객체 연산 및 캐시·메모리 접근이 누적 |

비교를 위한 **배열 형식 가정**으로 64비트 숫자를 연속 저장한다면 격자 하나는 8,000,000바이트(약 7.63 MiB), 세 격자는 약 22.89 MiB입니다. 현재 Python list는 이런 연속 숫자 배열이 아니며, 포인터·숫자 객체·행 목록 비용이 더해집니다. 값의 객체 공유 여부와 실행 환경에 따라 크기가 달라지므로 이 수치를 현재 프로그램의 실제 RAM 사용량으로 제시하지 않습니다. `sys.getsizeof()`도 참조한 내부 객체까지 자동 합산하지 않으므로 전체 프로세스 최대 메모리나 객체 구조를 고려해 측정해야 합니다. [Python sys.getsizeof 설명](https://docs.python.org/3.13/library/sys.html#sys.getsizeof)

우선순위는 **① 프로파일링 → ② 반복·접근 비용 감소 → ③ 데이터 표현·재사용 → ④ 필요 시 병렬화**입니다. 먼저 I/O와 검증을 분리한 연산 시간, 전체 로드 시간, 최대 메모리를 각각 측정합니다. 다음으로 각 행을 지역변수로 받아 반복 인덱싱을 줄이고, 두 필터의 점수를 한 번의 격자 순회에서 누적하는 방식을 기존 함수와 같은 입력으로 비교할 수 있습니다. 두 점수를 동시에 구해도 MAC 수는 `2N²`로 유지되지만 패턴 접근과 반복 제어 일부를 공유할 수 있습니다.

선택 과제의 1차원 표현이나 표준 라이브러리 `array` 등 연속 숫자 저장 방식도 후보입니다. 변환 비용과 변환 전후 격자가 함께 존재하는 최대 메모리까지 포함해 판단하고, 불변 필터를 케이스마다 다시 변환하지 않도록 재사용합니다. 많은 입력이라면 케이스별 읽기·처리로 전체 메모리를 줄이는 데이터 형식도 검토할 수 있습니다. 프로세스 분할은 직렬화·복사·부분합 병합 비용 때문에 항상 빠르지 않으므로 충분한 작업량에서만 비교합니다. 이들은 향후 최적화 전략이며 현재 구현이나 실측 성과로 주장하지 않습니다. 과제의 외부 라이브러리 금지와 반복문 직접 구현 조건도 유지해야 합니다.

### CPU 직렬 루프와 NPU 병렬 MAC의 병목 비교

| 관점 | 현재 Python CPU 시뮬레이터 | NPU 같은 전용 가속기의 일반적인 방식 |
| --- | --- | --- |
| 계산 배치 | 한 실행 흐름의 중첩 반복에서 곱하고 total에 누적 | 여러 MAC 처리 요소에 작업을 배치하고 부분합을 합침 |
| 주요 비용 | Python 반복·객체 연산·인덱싱, 누적 합의 의존성, 메모리 접근 | 연산 배열을 채우기 위한 데이터 공급·대역폭, 타일 간 이동·부분합 결합 |
| 데이터 재사용 | 현재는 필터별 순회와 Python list 접근 | 온칩 버퍼·타일 배치로 입력·가중치를 재사용하도록 설계 가능 |
| 작은 입력 | 호출 비용이 상대적으로 큼 | 장치 전송·실행 준비 비용이 이득을 상쇄할 수 있음 |

예를 들어 1000×1000의 한 필터는 백만 개의 위치별 곱을 누적해야 합니다. 현재 코드는 이를 반복문 순서대로 처리합니다. **가상의** 병렬 처리 요소가 P=1000개이고 데이터가 충분히 공급된다면, 곱셈 배치만 보면 대략 1000개씩 1000묶음으로 나눌 수 있습니다. 그러나 최종 합을 위한 부분합 결합과 메모리 공급·동기화가 필요하므로 실제 시간이 1000분의 1이 된다는 뜻은 아닙니다. 64비트 연속 저장을 가정해 입력과 필터를 각각 한 번 읽어도 한 필터당 약 16 MB를 공급해야 하며, 데이터 재사용과 대역폭이 병목이 될 수 있습니다.

CPU 자체에도 다중 코어와 SIMD 같은 병렬 기능이 있으므로 CPU가 본질적으로 직렬 전용이라고 일반화하지 않습니다. 여기서 직렬이라는 표현은 **현재 Python 루프의 실행 구조**를 뜻합니다. 전용 가속기의 구체적인 구성은 제품마다 다르며, 병렬 MAC 배열과 데이터 재사용의 사례로 Google TPU의 systolic array 구조를 참고할 수 있습니다. [Google 공식 TPU 구조 설명](https://docs.cloud.google.com/tpu/docs/system-architecture-tpu-vm)

어떤 방식에서도 처리해야 할 위치별 연산량 자체는 O(N²)입니다. 병렬화는 배치·실행 시간에 영향을 주며 수학적 작업량을 없애지 않습니다. 합산 순서나 정밀도가 달라지면 점수의 미세한 차이도 생길 수 있어, CPU·가속기 결과를 비교할 때 같은 데이터·정밀도·동점 정책으로 검증해야 합니다.
